Manage Profiles
Operation Endpoint Method Status
Upsert /api/profiles POST ✓ confirmed
Delete /api/data-privacy-deletion-jobs POST ⚠ 2 warnings ▾
Async execution. This endpoint queues a deletion job — it does not delete the profile immediately. The profile remains readable until the job processes. There is no webhook; to confirm deletion you must poll the job status endpoint.
Irreversible and rate-limited. Once the job completes, there is no undo and no soft-delete state. Rate limited at 60 requests/minute — bulk deletes require batching and backoff.
Download all /api/profiles (paginated) GET ⚠ multi-step ▾
Cursor-based pagination required. GET /api/profiles returns one page of results plus a next cursor in the response links. The agent loops — passing each response's cursor into the next request — until next is null. A single call does not return all profiles.
Page size and rate limits apply. Default page size is 20; max is 100 via the page[size] parameter. Rate limits apply per-call, not per-profile — large exports require pacing.
Manage Audiences — Lists
Operation Endpoint Method Status
Create list /api/lists POST ✓ confirmed
Add member /api/lists/{id}/subscribe POST ⚠ 2 paths ▾
Path A — Direct add
POST /api/lists/{id}/relationships/profiles
Adds the profile to the list immediately. Bypasses Klaviyo's consent layer — does not check opt-in status, GDPR suppression, or double opt-in flow. Use only when consent is captured externally and you are certain the contact is eligible.
Path B — Consent-aware add (recommended)
POST /api/profile-subscription-bulk-create-jobs
Respects Klaviyo's opt-in flow, GDPR consent state, and global suppressions. If the profile is suppressed, the add is silently skipped — no error returned. Async job, not immediate. This is the safe default for any consent-sensitive marketing list.
Where they intersect: both paths result in list membership if the add succeeds. Where they deviate: Path A ignores consent and is synchronous; Path B enforces it and is async. Adding a suppressed contact via Path A bypasses the suppression layer and may create a GDPR violation — the API will not prevent it.
Remove member /api/lists/{id}/relationships/profiles DELETE ⚠ 1 warning ▾
List removal ≠ global unsubscribe. This endpoint removes the profile from this specific list but does not suppress the contact account-wide. The profile remains active and reachable by other lists, flows, and campaigns. To suppress all future marketing, a separate call to the profile suppression endpoint is required.

Manage Segments
Operation Endpoint Method Status
Create segment /api/segments POST ⚠ rate limit ▾
Tight rate limit on segment creation. Klaviyo enforces a low rate limit on POST /api/segments. Creating one segment per user action is fine; programmatic bulk creation requires exponential backoff and is not designed for high-volume use.
API condition set is narrower than the UI. Some segment conditions available in the Klaviyo UI cannot be expressed through the API — the API supports a subset. Verify that your required conditions are API-expressible before building the workflow.
Read segment /api/segments/{id} GET ✓ confirmed
Add/remove member — — N/A by design ▾
Segments are rule-based — membership is computed, not written. Klaviyo evaluates each profile continuously against the segment's condition definition. There is no endpoint to manually add or remove an individual profile. Membership is a derived state, not a relationship you can store directly.
To include a profile: ensure their attributes satisfy the segment's conditions (e.g., "purchased in last 30 days," "city = Seattle"). To exclude a profile: update their attributes so they no longer match, or tighten the segment's rule definition. This is intentional — it is what makes segments self-updating without manual maintenance.
Contrast with Lists: Lists support direct membership management via /api/lists/{id}/relationships/profiles. If the workflow requires adding specific contacts by profile ID, use a List rather than a Segment.

Manage Contacts
Operation Endpoint Method Status
Create / Upsert /crm/v3/objects/contacts POST ⚠ 1 warning ▾
Silent duplicate on existing email. POST creates a new contact record every time — no 409 or dedup on email address. An existing contact at the same email becomes a duplicate in the CRM. Use the batch upsert endpoint with idProperty=email for safe dedup at any volume.
Update contact /crm/v3/objects/contacts/{contactId} PATCH ✓ confirmed
Archive contact /crm/v3/objects/contacts/{contactId} DELETE ⚠ 1 warning ▾
Archive ≠ hard delete. Archived contacts are hidden from search and list views by default but remain in the database. There is no permanent removal endpoint via CRM v3. If GDPR erasure is required, use the GDPR Delete endpoint under HubSpot's privacy compliance API instead.

Manage Lists
Operation Endpoint Method Status
Create list /crm/v3/lists POST ⚠ 1 warning ▾
processingType is permanent. MANUAL lists accept direct member writes via the memberships endpoint. DYNAMIC lists compute membership from a filter rule — member writes are silently ignored. This is set at creation and cannot be changed. Design for the list type before writing the create call.
Manage members /crm/v3/lists/{listId}/memberships PUT ⚠ 1 warning ▾
Silent 200 on DYNAMIC lists. Sending a PUT to the memberships endpoint on a DYNAMIC list returns HTTP 200 with no error — and does nothing. The contact is not added. Always check the list's processingType before writing members to avoid silent no-ops in pipelines that rely on write confirmation.
Delete list /crm/v3/lists/{listId} DELETE ✓ confirmed
Update list — — ⚠ 2 paths ▾
Path A — Rename
PUT /crm/v3/lists/{listId}/update-list-name
Updates the list's display name only. Works for both MANUAL and DYNAMIC lists.
Path B — Update filter rules
PUT /crm/v3/lists/{listId}/update-list-filters
Updates the filter condition set that determines DYNAMIC list membership. Only valid for DYNAMIC lists — has no effect on MANUAL lists.
No general PATCH endpoint. Name and filter rules are updated through two separate endpoints. For MANUAL lists, only the name can be changed. For DYNAMIC lists, changing filters changes computed membership — it does not add contacts manually.
Manage Associations
Operation Endpoint Method Status
Create associations /crm/v4/associations/…/batch/create POST ⚠ 1 warning ▾
Association type IDs are magic numbers. contact→company = 1, contact→deal = 3, contact→ticket = 16. These are not returned by the API in human-readable form. The v4 API provides a /types endpoint to enumerate them programmatically — use it to handle custom association types without hardcoding numeric IDs.
Read associations /crm/v4/associations/…/batch/read POST ✓ confirmed
Delete associations /crm/v4/associations/…/batch/archive POST ⚠ 1 warning ▾
Deleting without a type ID removes ALL associations between two objects. Include associationTypeId in the request body to scope the delete to a specific relationship type. Omitting it removes every association type between that pair — there is no confirmation step and no undo.
